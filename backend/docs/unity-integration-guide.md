# Unity Integration Guide — Patient Simulation Backend

This is the reference a Unity client developer needs to talk to this backend:
every endpoint, the exact request/response shapes, and — most importantly —
the **async reply pattern**, which is the one thing that will break a naive
Unity integration if it's not understood up front.

Two working reference clients already exist in this repo and are worth
running once against a live server before writing any Unity code, just to
see real traffic:

- `backend/scripts/test_voice_ws_live.py` — a terminal script that does the
  full session → WS connect → send → receive round trip.
- `voice-chat-tester.html` (repo root) — a browser page doing the same thing
  with a UI. Open it, point it at your server, and watch the Network/WS tabs
  in devtools while you use it.

## 1. The one thing to understand before anything else: replies are async

**Every patient reply is generated by an external AI service that takes
6–48 seconds per call.** Because of that, this backend does **not** hand you
the patient's reply in the same response as your request. Instead:

1. You `POST` a message (text or voice). The response comes back almost
   immediately (well under a second) with a **placeholder**:
   `status: "pending"` and empty content.
2. The real reply is generated in the background and delivered later over a
   **WebSocket** connection: `ws://<host>/ws/voice?session_id=<id>`.
3. You must have that WebSocket **already open** before you send the message
   — if it isn't connected yet, the push has nowhere to go and is silently
   dropped (nothing gets queued or redelivered).

**Practical rule for your Unity client**: open the WebSocket connection the
moment a session becomes active (right after `POST /sessions` succeeds, or
right after you decide to reuse an existing session id), and keep it open
for the entire time that session is in use — not just around one message.

```
Unity                                   Backend
  |--- POST /sessions ------------------->|
  |<-- 201 {session_id} ------------------|
  |--- WS connect /ws/voice?session_id= ->|
  |<-- WS open ----------------------------|
  |--- POST /sessions/{id}/messages ----->|
  |<-- 201 {status:"pending", ...} -------|   (respond to this fast, e.g. show "typing...")
  |                                        |   (6-48s pass; the RAG call happens here)
  |<== WS frame {"type":"thinking",...} ==|   (optional, only if it's taking a while)
  |<== WS frame {"type":"reply", status:"complete", content:"..."} ==|
  |<== WS binary frame (audio, voice turns only) ==|
```

A second message sent to the same session **before** the first reply has
arrived gets rejected with `409 Conflict` — the server only generates one
reply at a time per session. Disable your "send" button/action while a reply
is pending, and re-enable it once the WS delivers `"complete"` or `"failed"`
(or your own client-side timeout fires — see §4).

## 2. Base URL, auth, CORS

- No path prefix: every route below is relative to the server root, e.g.
  `http://<host>:8000/sessions`.
- **No authentication is required today.** There's an optional
  `Authorization` header slot in the reference test clients purely for future
  use; don't send anything and it'll work.
- CORS (`CORS_ORIGINS` in the server's `.env`) is a **browser-only**
  restriction — it does not apply to Unity's `UnityWebRequest`/native
  networking or to a native WebSocket client. Ignore any CORS-related notes
  you see in the browser test page's own comments; they're not relevant to a
  Unity build.

## 3. Session lifecycle — the endpoints, in the order you'll actually use them

| # | Method & path | Purpose |
|---|---|---|
| 1 | `GET /scenarios` | List available cases to let the trainee pick one |
| 2 | `POST /sessions` | Start a session for a chosen scenario |
| — | *(open WS here — see §1)* | |
| 3 | `POST /sessions/{id}/messages` or `POST /sessions/{id}/chat-voice` | One doctor turn (text or audio) |
| 4 | `GET /test-categories`, `GET /test-categories/{id}/tests`, `GET /scenarios/{id}/relevant-tests` | Investigation menu |
| 5 | `POST /sessions/{id}/tests` | Order an investigation |
| 6 | `GET /scenarios/{id}/questions` | Quiz questions for this scenario |
| 7 | `POST /sessions/{id}/answers` | Submit a quiz answer |
| 8 | `POST /sessions/{id}/evaluate` | Get an OSCE-style score for the session so far |
| 9 | `GET /sessions/{id}` | Full session review (transcript, ordered tests, answers with correctness) |

None of steps 4–8 require the WS connection — only the reply to step 3
arrives asynchronously over it. Steps 4–8 are ordinary synchronous
request/response calls.

### 3.1 `GET /scenarios`

Response: `200`, array of
```json
[{ "id": 2, "name": "Acalculous cholecystitis" }]
```
`case_text`/`gold_standard` are deliberately never exposed — this is only
enough to populate a scenario picker.

### 3.2 `POST /sessions`

Request:
```json
{ "scenario_id": 2 }
```
Response `201`:
```json
{ "session_id": "9342d217-1242-4e0b-a4b0-427a8ed69124" }
```
`404` if `scenario_id` doesn't exist. `session_id` is a string (UUID) — treat
it as an opaque token, not a number.

### 3.3 `POST /sessions/{id}/messages` — text turn

Request:
```json
{ "content": "Hello, what brought you in today?" }
```
Response `201` — **this is always the placeholder, never the real reply**:
```json
{ "id": 90, "role": "assistant", "content": "", "created_at": "2026-09-06T12:13:37.77Z", "status": "pending" }
```
`status` is one of `pending` → `generating` → `complete` | `failed`. The real
text lands later via WS (§5). `409` if a reply is already generating for
this session; `404` if the session doesn't exist.

### 3.4 `POST /sessions/{id}/chat-voice` — voice turn

Multipart/form-data, one field:

| Field | Type | Notes |
|---|---|---|
| `file` | binary | The recorded audio clip. Field name must be exactly `file`. |

No enforced format allow-list in this backend — confirmed from the route
handler itself: it reads the uploaded bytes and forwards them as-is to a
Whisper-based speech-to-text service, with no format check in between.
Whisper-based STT generally handles common container formats (`.wav`,
`.ogg`, `.mp3`, `.webm`) without extra work on your end, but that's a
statement about the STT model in general, not something verified end-to-end
against this project's live Colab-hosted instance in this session — test
whichever format your recording pipeline actually produces against a real
server early, rather than assuming. If you have a free choice, mono 16 kHz
WAV is the conventional safest bet for STT accuracy.

Response `200`:
```json
{
  "transcribed_text": "hello what brought you in today",
  "reply": { "id": 91, "role": "assistant", "content": "", "created_at": "...", "status": "pending" },
  "reply_audio_base64": null,
  "reply_audio_content_type": null
}
```
`transcribed_text` is real and immediate (speech-to-text runs synchronously
— it's fast). `reply_audio_base64`/`reply_audio_content_type` are **always
null** in this response — the real reply text *and* its synthesized audio
both arrive later over the WS connection (§5), as a JSON frame followed by a
binary frame. `502` if the STT service itself is unreachable/failing
(`VoiceServiceUnavailableError`) — this is a real upstream outage, distinct
from a normal validation error.

### 3.5 Investigations

- `GET /test-categories` → `[{ "id": 1, "name": "..." }]`
- `GET /test-categories/{category_id}/tests` → `[{ "id": 4, "category_id": 1, "name": "..." }]` — menu only, no `result` field (that would leak the answer before it's ordered).
- `GET /scenarios/{scenario_id}/relevant-tests` → same shape as above, but narrowed to tests this specific case actually has a finding for — a hint for your UI to highlight, **not** an allow-list (any test id from the global catalog can still be ordered against any scenario).
- `POST /sessions/{id}/tests` with `{ "test_id": 4 }` → `201`:
  ```json
  { "ordered_test_id": 12, "test_id": 4, "name": "...", "result": "...", "ordered_at": "..." }
  ```
  `result` only ever appears here, once ordered. `404` for an unknown `session_id` or `test_id`.

### 3.6 Quiz

- `GET /scenarios/{scenario_id}/questions` → `[{ "id": 1, "text": "...", "choices": [{ "id": 1, "text": "..." }] }]` — deliberately excludes which choice is correct.
- `POST /sessions/{id}/answers` with `{ "question_id": 1, "choice_id": 1 }` → `201`:
  ```json
  { "id": 5, "question_id": 1, "choice_id": 1, "answered_at": "..." }
  ```
  Note there is **no `is_correct` field here** — correctness is deliberately never revealed at submission time, only in the session review (§3.8). Re-submitting an answer for the same question replaces the previous one (upsert), it doesn't create a duplicate. `400` if `choice_id` doesn't belong to `question_id`.

### 3.7 `POST /sessions/{id}/evaluate`

No request body. Response `200`:
```json
{
  "score": 50.0,
  "summary": "...",
  "criteria_breakdown": [{ "name": "History taking", "passed": true, "feedback": "..." }]
}
```
Generated fresh on every call, not persisted/cached — call it as many times
as you want. `400` if the scenario has no reference answer configured
(`gold_standard`) — this is a content/authoring gap for that scenario, not a
client bug; show a clear "not gradable" state rather than treating it as an
error to retry.

### 3.8 `GET /sessions/{id}` — full review

```json
{
  "session_id": "...",
  "scenario_id": 2,
  "created_at": "...",
  "messages": [{ "id": 90, "role": "user", "content": "...", "created_at": "...", "status": "complete" }],
  "ordered_tests": [{ "id": 12, "test_id": 4, "name": "...", "ordered_at": "..." }],
  "answers": [{ "id": 5, "question_id": 1, "choice_id": 1, "is_correct": true, "answered_at": "..." }]
}
```
This is the only place `is_correct` ever appears. Useful for building an
end-of-session summary screen, or for polling a message's status if you'd
rather not hold a WS connection open the whole time (see §5's note on that
trade-off).

## 4. Timeouts you should mirror client-side

The server's own hard deadline for one reply generation is **65 seconds**
(`Settings.rag_patient_hard_timeout_seconds`). If generation is still running
after **15 seconds** (`Settings.rag_patient_filler_after_seconds`), you'll
get an interim `{"type": "thinking", ...}` frame — use it to show a "still
thinking" indicator rather than a spinner with no feedback for up to a
minute. If nothing has arrived after ~65s, the server itself gives up and
pushes a `status: "failed"` reply with a fixed fallback line — but build your
own client-side timeout too (75s is a safe margin) in case the WS connection
itself dropped and you never receive that final frame at all.

## 5. The WebSocket protocol in detail

Connect to `ws://<host>/ws/voice?session_id=<id>` (or `wss://` if the server
is behind TLS). `session_id` is a required query parameter — connecting
without one gets an immediate `{"type":"error",...}` frame and the socket
closes.

This one socket is used for **two** things, and you can freely mix them on
the same connection:
- **Pushing async replies** for turns you submitted via the REST endpoints
  above (§3.3/§3.4) — this is the only thing you actually need for a
  text-and-file-upload client.
- **Submitting voice turns directly**: send a binary frame containing one
  complete audio clip (not a raw streaming/PCM protocol — one frame = one
  full utterance) and the server runs the exact same voice-chat pipeline as
  `POST /chat-voice`, replying over the same socket.

### Frames you will receive

| `type` | When | Shape |
|---|---|---|
| `"transcript"` | Only right after *you* sent a binary audio frame on this socket | `{"type":"transcript","text":"..."}` |
| `"thinking"` | Generation still running after ~15s | `{"type":"thinking","id":90}` |
| `"reply"` (pending push shape — the one you'll actually see) | Once generation finishes | `{"type":"reply","id":90,"role":"assistant","content":"...","status":"complete","created_at":"..."}` |
| binary frame | Immediately after a `"reply"` frame with `status:"complete"`, **only for turns that went through chat-voice/a WS binary frame** (never for plain text messages) | Raw audio bytes, WAV |
| `"error"` | Bad/unknown `session_id`, or a busy-session conflict | `{"type":"error","code":"session_busy"?,"detail":"..."}` |

Two notes that will save you debugging time:

- **The `"reply"` frame's text field is `content`, not `text`**, when it
  arrives via the async push path (which is what you'll see for both
  `/messages` and `/chat-voice` submitted turns in production). There is a
  second, rarer frame shape — `{"type":"reply", "text": "...", "audio_content_type": "..."}`
  — but that one only ever occurs if a session is talking to a
  synchronous/test-only backend configuration, not the live server. Check
  for `content` first, fall back to `text` if absent, and you'll handle both
  correctly without needing to know which one you're getting.
- **`"error"` with `code: "session_busy"` does not close the socket.** Any
  other error does close it. Don't treat every `"error"` frame the same way
  — check `code` before deciding whether to reconnect.

### Correlating a frame to "which message is this reply for"

Every `"thinking"`/`"reply"` frame carries the same `id` you got back in the
`201` response from `POST /messages` or `POST /chat-voice` (`reply.id`).
Since the server only ever generates one reply per session at a time, in
practice you only ever need to track a single "currently pending message id"
per session — match incoming frames against that, and clear it once you see
`status` leave `"pending"`/`"generating"`.

### Reconnecting

If the socket drops mid-session (network blip, server restart), reconnect to
the same `ws://<host>/ws/voice?session_id=<id>` URL — it's stateless from the
connection's point of view; the session and its message history live in the
database, not in the socket. A reply that finishes generating while you're
disconnected is **not queued for redelivery** — a push with nothing
listening is a silent no-op, by design (see §1). Two consequences worth
building around:

- If you reconnect *before* generation finishes, you'll receive the push
  normally — no data is lost, you just have to be listening again in time.
- If you reconnect *after* it already finished, the WS push for that turn is
  gone for good, but **the data itself isn't** — the reply was already
  persisted to the database regardless of whether anyone was listening. Call
  `GET /sessions/{id}` (§3.8) after reconnecting (or on any prolonged
  disconnect) to recover the actual final `status`/`content` for the message
  you were waiting on, rather than assuming a missed WS frame means a lost
  reply.

Show the trainee a clear connecting/connected/disconnected/error indicator;
don't retry silently forever — see `voice-chat-tester.html`'s reconnect
button for a minimal reference implementation of this.

## 6. Utility endpoints (outside the main flow)

- `GET /health` → `200 {"status":"ok","database":"ok"}`, or `503` if the
  database itself is unreachable. Good for a startup connectivity check
  before you show the scenario picker.
- `POST /transcribe` — multipart `file` field, same as §3.4 — returns just
  `{"text": "..."}` with no session/reply involved. Useful for testing your
  recording pipeline's audio format against the real STT service in
  isolation, without needing a session at all.

## 7. Error status codes, summarized

| Status | Meaning | What to do |
|---|---|---|
| `400` | Validation error, or a domain rule was violated (e.g. answer choice doesn't belong to the question, or `/evaluate` called on a scenario with no reference answer) | Show the `detail` message; don't retry blindly |
| `404` | `session_id`/`scenario_id`/`test_id`/`question_id` doesn't exist | Almost always a client bug (stale/typo'd id) — check what you're sending |
| `409` | A reply is already being generated for this session | Wait for it to settle (WS push or your own timeout), then retry the same request |
| `502` | The upstream speech-to-text or text-to-speech service is unreachable/failing | Real infrastructure issue, not yours — show a "voice service unavailable" state; text-only chat is unaffected |

Every error body is `{"detail": "<human-readable message>"}`.

## 8. Practical notes for building this in Unity/C#

- **REST calls**: `UnityWebRequest` for everything in §3. For
  `chat-voice`'s multipart upload, use `UnityWebRequest.Post(url, form)` with
  a `WWWForm`/`List<IMultipartFormSection>` containing one
  `MultipartFormFileSection("file", audioBytes, "recording.wav", "audio/wav")`
  — the field name must be `file`, matching §3.4.
- **WebSocket**: Unity's built-in networking does **not** include a
  WebSocket client (and `System.Net.WebSockets` isn't available on every
  Unity scripting backend/platform, notably WebGL). Use a third-party
  package — `NativeWebSocket` (MIT, works across IL2CPP/WebGL/mobile) is a
  common choice for exactly this reason; any client that supports both text
  and binary frames and lets you set `binaryType`/read raw bytes works.
- **JSON**: any of `Newtonsoft.Json`, `System.Text.Json` (via a plugin), or
  hand-rolled parsing will do — the payloads are small and flat. Watch out
  for `MessageRead.status` and the WS frame `type`/`status` fields if you use
  strongly-typed deserialization with strict enums: new status/frame values
  could be added later, so deserialize permissively (a plain `string`, not a
  closed enum) and handle unknown values gracefully rather than throwing.
- **Audio playback**: the binary WS frame (and, on the synchronous test-only
  path, `reply_audio_base64`) is a raw WAV byte stream — decode with
  `WWW.audioClip`/`UnityWebRequestMultimedia`, or any WAV parser, into an
  `AudioClip` for playback.
- **State machine shape**: model the compose UI as *idle → sending → pending
  reply (disabled) → settled (idle again)* per session, exactly mirroring
  what `voice-chat-tester.html`'s `state.pending` object does — that file is
  a complete, runnable reference for this exact state machine if you want to
  see it working end to end before writing Unity code.
