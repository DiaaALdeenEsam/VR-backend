هذا المستند يشرح كيف بُنيت الواجهة الخلفية (backend) لمحاكي المريض — بنيتها المعمارية، وقرارات التصميم الأساسية — ثم يقدّم دليلاً عمليًا لاختبار كل نقطة نهاية (endpoint) في الـ API خطوة بخطوة، بأمثلة curl جاهزة للنسخ، وصولًا إلى تجربة الحديث المباشر مع نموذج Qwen المحلي الذي يقف خلف ردود "المريض".

لمحة عامة

المشروع عبارة عن backend لمحاكاة مريض افتراضي يتدرّب عليه الأطباء: يقرأ الطبيب حالة سريرية، يحاور "المريض" عبر رسائل، يطلب فحوصات (علامات حيوية، تحاليل، أشعة...)، ثم يجيب عن أسئلة تشخيصية تُقيَّم لاحقًا. سابقًا كان هذا سيُبنى على ملفات JSON متفرقة وقواميس في الذاكرة — الآن كل شيء مخزَّن في قاعدة بيانات SQLite حقيقية، عبر طبقة ORM (SQLModel) ومخطط تُديره هجرات Alembic فعلية، لا create_all().

الكيانات الأساسية في النموذج:

  • Scenario — الحالة السريرية (نص الحالة مخفي، لا يُعاد أبدًا عبر API)
  • TestCategory / Test — تصنيفات وفحوصات، لكل فحص نتيجة تُكشف فقط عند الطلب
  • Question / Choice — أسئلة تشخيصية وخياراتها، مع مفتاح إجابة صحيحة لا يُكشف أبدًا مسبقًا
  • Session / Message — جلسة تدريب وسجل المحادثة الخاص بها
  • OrderedTest / Answer — سجل الفحوصات المطلوبة، وإجابات الطبيب (بترقية/upsert عند إعادة الإجابة)

البنية المعمارية

الكود مقسَّم إلى أربع طبقات نظيفة (Clean Architecture)، بحيث تعرف كل طبقة فقط ما يليها إلى الداخل، ولا شيء يعرف عن الطبقات الخارجية:

api
infrastructure
application
domain
اتجاه الاعتماد يتجه دائمًا إلى الداخل

domain — كيانات Python صرفة (dataclasses) وواجهات مستودعات مجرّدة، بلا أي استيراد لـ SQLModel أو FastAPI.

application — حالة استخدام واحدة لكل ملف (بدء جلسة، طلب فحص، إجابة سؤال...)، تعتمد فقط على واجهات الـ domain عبر حقن المُنشئ (constructor injection).

infrastructure — نماذج SQLModel الفعلية، محرك القاعدة غير المتزامن، وتنفيذ المستودعات الذي يترجم بين صفوف القاعدة وكيانات الـ domain.

api — راوترات FastAPI رقيقة: تستقبل الطلب، تستدعي حالة الاستخدام، وتُحوّل الناتج إلى مخطط استجابة — بلا أي منطق عمل.

قرارات تصميم مهمة

  • لا تسريب لنتائج الفحوصات: حقل result لا يظهر في قائمة الفحوصات (GET /test-categories/{id}/tests)، بل فقط بعد طلب الفحص فعليًا ضمن جلسة.
  • لا تسريب لمفتاح الإجابة: correct_choice_id لا يُعاد أبدًا عبر GET /scenarios/{id}/questions، ولا يوجد endpoint مخصص لكشفه.
  • لا تسريب لصحة الإجابة عند إرسالها: الرد على POST /sessions/{id}/answers لا يحتوي is_correct — تظهر فقط لاحقًا عبر مراجعة الجلسة الكاملة.
  • معاملة واحدة لكل عملية كتابة: عبر نمط Unit of Work، كل حالة استخدام معدِّلة (بدء جلسة، طلب فحص، إجابة) تُنفَّذ بالكامل أو تُلغى بالكامل — لا كتابة جزئية عند حدوث خطأ.
  • ترقية الإجابات (upsert): إعادة الإجابة على نفس السؤال ضمن نفس الجلسة تستبدل الإجابة السابقة، لا تُنشئ سجلًا مكرَّرًا.
  • الهجرات هي مصدر الحقيقة: لا استدعاء لـ create_all() في أي مكان — المخطط بالكامل يُبنى عبر Alembic، بما يشمل قاعدة SQLite داخل الذاكرة المستخدمة في الاختبارات.
  • رد المريض معزول خلف واجهة (port): PatientReplyGenerator هي الواجهة الوحيدة التي تعرفها طبقة الـ application. حاليًا يوجد تنفيذان فعليان لها في app/infrastructure/: نموذج Qwen المحلي (الافتراضي)، ونموذج بديل ثابت (stub) للاختبارات السريعة. التبديل بينهما سطر إعداد واحد فقط — التفاصيل أدناه.
  • التقييم منفصل بنفس المبدأ: EvaluationGenerator واجهة مستقلة أخرى (نموذج بديل ثابت حاليًا في app/infrastructure/stub_evaluator.py)، تُستهلَك بواسطة EvaluateSessionUseCase ولا تُخزَّن نتيجتها في قاعدة البيانات — تُولَّد عند كل استدعاء لـ POST /sessions/{id}/evaluate.

التحدث مع النموذج مباشرة (Qwen)

منذ التحديث الأخير، رد "المريض" في POST /sessions/{id}/messages لم يعد نصًا ثابتًا — هو رد فعلي من نموذج لغوي محلي صغير، Qwen/Qwen2.5-0.5B-Instruct، يعمل بالكامل على جهازك عبر transformers وtorch (على المعالج CPU، بلا حاجة لكرت شاشة). أربع طرق لتجربته والتأكد أنه يعمل فعليًا، من الأسهل إلى الأدق:

1

محادثة كاملة عبر الخادم الفعلي (curl)

ابدأ جلسة، ثم أرسل عدة رسائل متتالية بنفس معرّف الجلسة — كل رسالة تُخزَّن، والنموذج يرى سجل المحادثة السابق عند توليد كل رد (آخر 8 رسائل كحد أقصى). 

# 1) ابدأ جلسة
curl -X POST http://127.0.0.1:8000/sessions \
  -H "Content-Type: application/json" \
  -d '{"scenario_id": 1}'
# → {"session_id": "SESSION_ID"}

# 2) حادث "المريض" -- استبدل SESSION_ID بالقيمة أعلاه
curl -X POST http://127.0.0.1:8000/sessions/SESSION_ID/messages \
  -H "Content-Type: application/json" \
  -d '{"content": "أين يؤلمك بالضبط؟"}'

curl -X POST http://127.0.0.1:8000/sessions/SESSION_ID/messages \
  -H "Content-Type: application/json" \
  -d '{"content": "منذ متى بدأ الألم؟"}'

مثال حقيقي من تشغيل فعلي للمشروع (وليس نصًا وهميًا) -- لاحظ الطلب الأول أخذ نحو 15 ثانية (تحميل النموذج لأول مرة في العملية)، والثاني نحو 5 ثوانٍ فقط:

الطبيب هل تعاني من ألم في المعدة؟
المريض (Qwen) نعم، أعاني من آلام في المقدسة. أشعر أنني أحتاج إلى المزيد من الرعاية الطبية.
الطبيب متى بدأ الألم؟
المريض (Qwen) بدأ الألم عند الساعة الثانية عشرة مساءً.
2

واجهة Swagger التفاعلية

شغّل الخادم وافتح http://127.0.0.1:8000/docs، وسّع POST /sessions/{session_id}/messages، اضغط Try it out، واكتب رسالتك -- لا حاجة لـ curl أو أي أداة خارجية، والرد يظهر مباشرة في المتصفح.

3

سكربت بايثون مباشر (بدون خادم HTTP إطلاقًا)

الأسرع لتجربة النموذج نفسه أو ضبط الـ prompt -- يستدعي QwenPatientReplyGenerator مباشرة دون المرور بطبقة الـ API أو قاعدة البيانات إطلاقًا: 

python -c "
import asyncio
from app.domain.entities import Scenario
from app.infrastructure.qwen_patient_generator import QwenPatientReplyGenerator

async def main():
    gen = QwenPatientReplyGenerator()
    scenario = Scenario(
        id=1, name='التهاب الزائدة الدودية الحاد',
        case_text='مريض عمره 22 عامًا يشكو من ألم حاد في الربع السفلي الأيمن من البطن منذ 12 ساعة.',
        gold_standard='التهاب الزائدة الدودية الحاد',
    )
    reply = await gen.generate_reply(scenario, history=[], user_message='أين يؤلمك بالضبط؟')
    print(reply)

asyncio.run(main())
"
4

عبر pytest -- الاختبار الآلي

tests/test_qwen_patient_generator.py يشغّل النموذج الحقيقي فعليًا (لا محاكاة/mock): توليد رد عربي غير فارغ، محادثة بسياق سابق، مسار التعطّل الآمن (fallback) عبر تعطيل التحميل عمدًا، وطلب HTTP كامل عبر POST /sessions/{id}/messages مع Qwen فعليًا. يتخطّى (skip) نفسه تلقائيًا -- لا يفشل -- إن لم يتوفر torch/transformers أو الاتصال بالإنترنت في بيئة التشغيل. 

pytest tests/test_qwen_patient_generator.py -v

التبديل بين Qwen والنموذج البديل الثابت

مفتاح الإعداد PATIENT_REPLY_BACKEND في ملف .env يتحكم بالتنفيذ المستخدم فعليًا (app/api/deps.py): 

PATIENT_REPLY_BACKEND=qwen   # الافتراضي -- نموذج Qwen المحلي الحقيقي
PATIENT_REPLY_BACKEND=stub   # رد ثابت بلا أي اعتماد على ML، للاختبارات السريعة فقط

مجموعة الاختبارات العامة (test_scenarios.py، test_sessions_flow.py) تستخدم stub افتراضيًا عبر override في tests/conftest.py -- لأنها تختبر تدفّق قاعدة البيانات لا جودة النموذج، فتبقى سريعة وحتمية النتيجة.

أول استخدام يُنزّل نحو 1GB من الأوزان إلى ~/.cache/huggingface (يحتاج اتصالًا بالإنترنت لمرة واحدة فقط، ثم يبقى محفوظًا محليًا). إن تعذّر ذلك -- لا اتصال، مساحة قرص غير كافية، أو أي عطل أثناء التوليد -- QwenPatientReplyGenerator لا يُسقط الطلب أبدًا، بل يعيد ردًا بديلًا واضحًا بدلاً من ذلك: 

[تعذّر توليد رد النموذج المحلي حاليًا] بخصوص سؤالك: أين يؤلمك بالضبط؟
ملاحظة صادقة حول الجودة: بحجم 0.5B معامل، هذا نموذج صغير جدًا مخصص للتطوير والاختبار فقط -- عربيته حقيقية ومفهومة غالبًا، لكنه أحيانًا يخرج عن الشخصية أو يُصيغ جملة بشكل غريب (مثال حقيقي آخر من نفس الجلسات التجريبية: على سؤال "منذ متى بدأ الألم؟" أجاب "أعتذر، لكن المعلومات التي قدمتها لم تكن موثقة..." بدلاً من إجابة مباشرة). هذا سلوك متوقع لنموذج بهذا الحجم، وليس خللًا في الربط التقني -- الهدف إثبات تدفّق كامل يعمل فعليًا، لا محادثة سريرية دقيقة.

وثائق تفاعلية إضافية (Swagger UI) متاحة أثناء تشغيل الخادم على /docs. جميع الأمثلة أعلاه مأخوذة من تشغيل فعلي للمشروع، وليست بيانات تجريبية وهمية.
